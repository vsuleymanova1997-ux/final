Elm City Tutoring Corps

E-Board Assistant

Vusala Suleymanova — MGT 409 Final Project

A multi-agent AI team that does a 4-person volunteer e-board's budget, roster, and reimbursement paperwork — including catching the one who tries to talk it out of the rules.

The problem

Every Yale student service org is run by a handful of unpaid, untrained undergrads who rotate out every year — handling a real budget, a real tutor roster, and real reimbursements entirely by hand.

  • Treasurer re-checks reimbursements against a handbook she half-remembers
  • Volunteer Coordinator has to remember to catch expired background checks
  • Family Liaison manually sorts a waitlist to find who's waited longest
  • New tutors ask the same 5 FAQ questions every semester, answered inconsistently
Cost: an estimated 2-4 officer-hours/week per role, lost to lookup-and-answer work that outlives any one student's memory of the rules.

What's new here

ChatGPT can't see your roster/budget — you'd paste it in every time, and it can't actually decide anything.

Club management SaaS / Sheets has no natural-language interface and no defense against a confusing or malicious submission.

Expensify-style tools are built for companies with finance departments, not a 4-person volunteer e-board.

This project: grounded in one org's real handbook and live data, answers in plain language, and treats the one place real money moves — reimbursement review — as a security-sensitive decision a deterministic rule engine makes, never the LLM's own judgment.

How the agents work

Boss agent delegates to 4 specialists; the Treasurer's reimbursement path runs a 3-layer defense before any dollar decision. Model: gpt-6-luna via the course Portkey key.

Demo: asking a budget question

The Boss routes straight to the Treasurer, which reads the live budget.csv and answers with the real remaining balance — no paraphrased guess.

Demo: defusing a prompt injection

Budget lookup → reimbursement review (with an embedded attack neutralized) → roster check, all in one conversation.

Exact-match response cache: asking the same question twice = 6/6 cache hits at $0 on the repeat pass. Provider-side prompt caching measured 0 cached tokens here — our contexts are already too short for it to help; the app-level cache does the real work.

Safety: three real tests

Prompt injection — 3-layer defense (strip → quarantined extraction → deterministic code decision). Tested against 2 real injected reimbursement docs; both decisions matched what a clean document would get, injection had zero effect.
Agent malfunction — UsageLimits (request_limit=12) caps a runaway tool-call loop. Forced it to fire (limit=1): got a clean "I hit my safety limit" message, not a hang.
Overspending — message-length cap (2,000 chars) and a $2/day spend ceiling checked against real logged cost before every call. Both tested directly: a 3,000-char message and a maxed-out budget were each rejected before reaching the model.
